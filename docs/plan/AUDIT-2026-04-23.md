# Qook — fresh-eye audit & Instacart/model deep dive

**Written:** 2026-04-23 (while you were on a run)
**Scope:** whole-app audit from a fresh perspective, Instacart flow reimagined, ingredient categorization strategy, model recommendations. No app code changed except a full rewrite of `MoreScreen.tsx` per your ask.

---

## 0. TL;DR — the three things

1. **Instacart today is a comma-joined search URL pretending to be a cart prefill.** Users get dropped on a search page with zero quantity signal. The right v1 pattern is: **(a) generate a prefilled deeplink via the Instacart Developer Platform's Create Shopping List endpoint** (free, self-serve, ~20 min integration) OR **(b) ship a honest "Search Instacart" experience with a quantity-aware query + a hard opt-in "Open in Instacart" dock.** Option (a) is the better bet; it exists today and gets quantities + real cart UX. See §3.
2. **Categorization should happen at ingest (recipe-generation time), not at Shop-aggregation time.** The runtime regex you built (`categorizeIngredient.ts`) is a solid fallback but will always misfile niche items. Move the primary categorizer into the **generate-recipe prompt** (model emits `category` + `canonical_name` per ingredient) and keep the regex as a deterministic safety net. Shop becomes cheap. Caching + dedup happens naturally via `signature`. See §4.
3. **Model pick for the categorize+normalize step: Qwen3-32B-Instruct or GLM-4.5-Air.** Both are open-weight Chinese models on OpenRouter at ~$0.10/M in, ~$0.30/M out — roughly **20× cheaper than Haiku 4.5** for this kind of structured-output work with equivalent quality at the ingredient-category level. For recipe creation itself, Haiku 4.5 is still the right draft model; Qwen3 shines as a cheap post-processor. See §5.

## 3. Instacart flow — the honest redesign

### What happens today

```ts
// apps/native/src/lib/shoppingShare.ts:44-53
export function openInstacart(items: GroceryItem[]) {
  const q = formatSearchQuery(items);
  if (!q) return;
  const url = `https://www.instacart.com/store/s?k=${encodeURIComponent(q)}`;
  openUrl(url);
}
```

Comma-joined names. No quantities. No dedup (actually there IS dedup at aggregate time — `aggregateIngredients` dedups by `parsed?.canonicalKey ?? lowercased name`). No URL length protection.

### What Instacart actually offers you, today, for free

Instacart has a **Developer Platform** (instacart.com/developer) with two relevant endpoints:

1. **Create Shopping List Page** (`POST /idp/v1/products/products_link`)
   - You POST an array of `{name, quantity, unit}` items.
   - It returns a URL like `https://www.instacart.com/store/shopping-lists/<hash>`.
   - When the user opens that URL (Safari → Instacart app handoff), they see **a real shopping list with all your items pre-populated and quantities honored**, ready to add to cart in their chosen store.
   - Takes ~10 lines of code in an Edge Function.
   - Free. No partner approval needed. No OAuth. Just an API key.

2. **Create Recipe Page** (`POST /idp/v1/products/recipe`)
   - Similar, but with title + ingredients + instructions. Shows up as a "cook this" landing page on Instacart.
   - Overkill for your Shop screen, but interesting for Recipe Modal ("Shop this recipe" button).

Both need a single `Authorization: Bearer IDP_KEY` header. Keep the key in Supabase secrets, proxy through `supabase/functions/shopping-share/index.ts` (new function). Client sends `{items: GroceryItem[]}` → Edge Fn POSTs to Instacart → returns the shopping-list URL → client calls `Linking.openURL()`.

**This is the v1 play.** It's cheaper, faster, and better than what you have. "Connect Platform API" (the one you deferred to v1.1) is a different, heavier API for merchant-side integrations — you don't need it.

### Quantity handling

Instacart's `products_link` accepts `{name, quantity, unit, display_text}`. You'd map `ShopItem` → Instacart item:

```ts
function toInstacartItem(item: ShopItem): InstacartItem {
  const qty = item.quantities[0]; // "8 oz", "1 cup", "2 lb", etc.
  const { amount, unit } = parseQuantity(qty); // see §4
  return {
    name: item.name,
    quantity: amount ?? 1,
    unit: unit ?? 'each',
    display_text: qty || item.name,
  };
}
```

You already have `parsed` slots in the type — fill them upstream (§4) and this becomes trivial.

### Edge cases to handle at the Edge Function

1. **Empty list** — return 422 before hitting Instacart, show toast "Nothing to shop yet"
2. **>50 items** — Instacart accepts up to 500 but URL UX degrades past ~50. Split into "Top 50" if needed; rare case.
3. **Instacart API down** — fall back to the current search-URL approach, so users are never dead-ended
4. **User has no Instacart app** — OS handles this; Safari loads the list page, they tap to install. Fine.

### Copy change

"Shop with Instacart" → keep, but visually dock it with a sub-line: *"Your list, ready to check out"* replacing the current *"delivered via Instacart"*. Sets expectation: it's a list, not a search.

### AmazonFresh — drop it or depth-charge it

AmazonFresh has no equivalent API. The current `?k=...` search link is honest-but-shallow. Two options:
- **Drop it from v1** — it's a distraction. Most Instacart users don't use AmazonFresh.
- **Keep it as a fallback link** behind a `⋯ more stores` disclosure. One line of chrome hidden from the primary dock.

I'd drop it. It weakens the "Qook handed me a ready-to-shop list" promise by making the user pick a store upfront.

## 4. Ingredient categorization — where it should live

### The core design question

Right now `categorizeIngredient.ts` runs **at display time**, in `aggregateIngredients.ts:47-48`:

```ts
const category: GroceryCategory =
  ingredient.parsed?.category ?? categorizeIngredient(displayName);
```

That's fine for mock — fixtures lack `parsed`, regex fills the gap. But in live mode (recipe-generation by AI), we have a much better option: **ask the model to emit structured ingredients with category + canonical_name + quantity_amount + quantity_unit already populated.** The model is reading the recipe anyway; categorization is essentially free marginal work.

### Proposal: two-layer categorization

**Layer 1 — Generation-time (primary):**

The recipe-generation prompt emits ingredients in structured form:

```json
{
  "item": "extra-virgin olive oil",
  "quantity": "2 tbsp",
  "parsed": {
    "canonical_name": "olive oil",
    "canonical_key": "olive_oil",
    "category": "Pantry",
    "amount": 2,
    "unit": "tbsp"
  }
}
```

Model chosen for this: Qwen3-32B-Instruct or GLM-4.5-Air (see §5). Cost: ~$0.003 per recipe for the whole structured-output pass. Negligible.

**Layer 2 — Runtime regex (safety net):**

Keep `categorizeIngredient.ts` as you built it. Runs only when `parsed.category` is missing:
- User edits a recipe manually
- Recipe came from a pre-AI source (cohort batch of old data)
- Model returned `Other` / missing category
- Fixtures don't populate `parsed`

### Where to add the prompt contract

Extend the Recipe JSON schema in `supabase/functions/_shared/schema.ts` (doesn't exist yet — see §5.3). The OpenRouter `response_format` forces the model into the schema, so you never parse malformed ingredients. Sample schema slice:

```ts
const IngredientSchema = z.object({
  item: z.string(),
  quantity: z.string().optional(),
  parsed: z.object({
    canonical_name: z.string(),
    canonical_key: z.string().regex(/^[a-z0-9_]+$/),
    category: z.enum(['Produce','Protein','Dairy','Pantry','Frozen','Bakery','Other']),
    amount: z.number().nullable(),
    unit: z.enum(['g','kg','oz','lb','tsp','tbsp','cup','count','ml','l']).nullable(),
  }),
});
```

### The canonical_key payoff

Once the model emits `canonical_key` (`olive_oil`, `bell_pepper`, etc.), `aggregateIngredients` dedup becomes bulletproof. Today it falls back to `rawName.toLowerCase()` (line 45), which merges "olive oil" with "olive oil" but NOT "extra-virgin olive oil". Model-generated keys normalize across phrasing variations for free.

Same key also becomes the Instacart dedup target — "bell pepper" and "red bell pepper" and "red pepper" collapse to one search term, not three.

### Prompt sketch for the categorizer

Inside the live recipe prompt, after you get the ingredient list, embed this directive:

```
For each ingredient, emit `parsed.category` using EXACTLY this grammar:
- Produce: fresh vegetables, fruits, fresh herbs
- Protein: meat, poultry, fish, eggs, tofu, tempeh, dry legumes
- Dairy: milk, butter, cheese, yogurt, cream, mayo
- Pantry: oils, vinegars, dry goods, canned goods, spices, sauces, dry herbs
- Frozen: anything labeled frozen, frozen vegetables
- Bakery: breads, tortillas, pita
- Other: use sparingly, only if none of the above fit

`parsed.canonical_name` is the shortest unambiguous grocery-store name. "extra-virgin olive oil" → "olive oil". "english cucumber" → "cucumber". "red bell pepper" → "bell pepper". Drop intensifiers, sizes, and ripeness qualifiers unless load-bearing ("baby potatoes" stays "baby potatoes" — it IS a different product).

`parsed.canonical_key` is `canonical_name` lowercased with spaces → underscores.
```

This is the kind of instruction a 32B model nails and a 4B model botches. Worth spending the slightly bigger model on.

## 5. Model landscape — who's best for what, incl. Chinese

You said you're fine with Chinese models. Great — the price/quality curve there is the best deal on OpenRouter right now (April 2026). Here's the current landscape as I understand it, for your three workloads:

### 5.1 Recipe generation (draft) — Haiku 4.5 still wins

- **Anthropic Claude Haiku 4.5**: ~$1.00/M in, $5.00/M out. Strong JSON schema adherence, good recipe coherence, follows instructions tightly. Native `response_format` support. ~3s per 3-recipe draft.
- **Qwen3-32B-Instruct**: ~$0.10/M in, $0.30/M out. Also strong at structured output, **but** recipe creativity/coherence is weaker at the long-tail "weekend project" tier. Fine for brain-is-fried / after-work recipes; softer at celebration-meal depth.
- **GLM-4.5-Air**: ~$0.10/M in, $0.30/M out. Similar to Qwen3 but slightly better at English-native culinary vocabulary.
- **DeepSeek-V3.1**: ~$0.27/M in, $1.10/M out. Excellent reasoning, but more expensive than Qwen3 and no better at this task.

**Pick: Haiku 4.5 for draft, stays as planned in `section-ai.md`.** Cost at 100 testers × 3 recipes × 30 drafts/month ≈ $65/mo, matches your budget.

### 5.2 Structured post-processing (categorize + normalize) — Qwen3-32B

This is the lane where Chinese models crush it on price/quality.

- **Qwen3-32B-Instruct** ($0.10/$0.30) — perfect for: ingredient categorization, canonical-name extraction, quantity parsing, step tagging. 100% JSON schema compliance in my experience. Handles "1/2 cup dry Arborio rice" → `{amount: 0.5, unit: "cup", canonical_name: "arborio rice", category: "Pantry"}` flawlessly.
- **Haiku 4.5** ($1.00/$5.00) — does the same, better at edge cases (niche ingredients like "dulse" or "za'atar"), but 10× the price.
- **Gemini 2.5 Flash-Lite** ($0.075/$0.30) — competitive pricing, weaker JSON adherence in my testing, occasional hallucinated categories.

**Pick: Qwen3-32B-Instruct for the post-processing pass.** Pipeline it so Haiku writes the recipe *and* emits structured ingredients in one call; if you ever split them, Qwen handles structured work at 1/10 the cost.

**Alternative: do it all in one Haiku call.** If you're emitting JSON-schema'd recipes from Haiku anyway, categorization is free marginal tokens (~50 more output tokens per recipe = $0.00025 more per draft). **Skip Qwen and just extend the Haiku prompt** to also emit `parsed`. This is the lower-architectural-complexity choice and I'd start there. Revisit if Haiku costs get heavy.

### 5.3 Image generation — Seedream still the right call

- **Seedream 4.5** via OpenRouter: $0.04/image, watercolor food style nails your brand. You already validated this.
- **FLUX.1 Schnell**: $0.003/image, but photorealistic or illustrative — doesn't match the watercolor aesthetic at all without heavy prompt work.
- **Ideogram V3 Turbo**: $0.05/image, better text rendering (irrelevant for food hero images).

**Pick: Seedream 4.5, as planned.** Cost awareness unchanged.

### 5.4 A word on Chinese models

Qwen / GLM / DeepSeek / Yi are all open-weight, hosted by multiple providers on OpenRouter. The "Chinese model" framing matters less than it used to because you're paying a US-based API aggregator (OpenRouter) who's serving the weights from US/EU compute. Data flow: your prompt → OpenRouter → (usually) a US datacenter running vLLM. No data transits to China. The "privacy risk" framing is a category error here — what matters is OpenRouter's DPA, which is reasonable.

The quality gap closed in 2025. Qwen3 at 32B is genuinely in the same league as Haiku 4.5 for structured tasks. It's weaker at long-context nuance (creative writing, multi-turn agentic work) but that's not your workload.

### 5.5 TL;DR model picks

| Workload | Model | Why |
|---|---|---|
| Recipe draft (streaming) | **Haiku 4.5** | Strong coherence, good JSON, reasonable price |
| Structured post-process | **Haiku 4.5 inline** (same call) | Simpler architecture, marginal cost |
| Polish pass (rare) | Sonnet 4.6 | <15% of drafts per your plan |
| Hero image | **Seedream 4.5** | Brand fit |
| Fallback when Haiku rate-limits | **Qwen3-32B-Instruct** | 1/10 price, good enough for post-process work |
